# CareFlow 投资人说明书

版本：0.1.0 开发增量  
文档用途：帮助投资人理解产品方向、技术资产和商业化假设，不构成收益承诺、审计报告或证券发行文件。

## 一、项目概览

CareFlow 是面向企业内部的知识库基础设施。它把企业分散的文档、表格、扫描资料和图片，转化为可授权、可检索、可引用、可审计的知识服务，并通过 Java 和 Python 公共接口供企业应用接入。

产品采用“独立知识库底座 + 可扩展应用层”架构：底座负责资料、权限、检索、引用、版本和治理；不同业务的意图识别、流程路由和 Agent 工具由上层应用独立配置。这样可以让同一份可信知识服务于客服、售后、研发、培训、合规等多个场景，同时避免把某个业务流程硬编码进基础设施。

当前产品优先保证单机、低并发环境下的功能正确、权限隔离和数据可追溯，不以高并发指标、高可用 SLA 或 GPU 调度作为当前版本承诺。

## 二、客户问题

企业已经拥有大量资料，但员工仍然依赖群聊、个人经验和重复询问，主要原因包括：

1. 文档分散在网盘、邮件、Wiki 和本地目录中，难以统一管理。
2. PDF、表格、扫描件和图片中的有效信息难以直接搜索。
3. 普通搜索只能返回关键词，不能解释答案来自哪里。
4. 资料有版本、有效期和访问范围，错误引用可能带来业务与合规风险。
5. 许多 RAG 产品重视“能回答”，却没有完整的发布、撤权、删除、审计和恢复流程。
6. 企业应用需要接入知识能力，但不希望每个应用重复建设解析、检索、权限和计量系统。

CareFlow 关注的是“答案是否有依据、是否对人可见、是否仍然有效、是否可以追责”，而不只是生成一段看似流畅的文字。

## 三、产品解决方案

### 1. 资料到知识的完整生命周期

文件上传后经过解析、OCR、结构清洗、Token 切片、质量检查、索引和人工发布。每个切片保留文档版本与来源位置；新版本可以先审核，旧版本继续服务，发布后再切换。

### 2. 多路检索与可验证回答

系统支持关键词 BM25、语义向量和混合 RRF 检索，并可使用 Rerank 和类型化元数据过滤。回答只使用通过权限和有效期校验的证据，返回引用位置；没有足够证据时明确拒答或提示资料不足。

### 3. 企业级权限与治理

企业、成员、角色、应用凭证、知识库和文档权限均按租户隔离。系统提供 OIDC 外部身份绑定、MFA、凭证期限与轮换、审计、数据保留、脱敏、删除影响预览、物理清理和备份恢复流程。

### 4. 面向应用的公共底座

Web 只调用公共 Java API；Java 管理身份、授权、元数据、任务、发布和计量；Python Worker 负责解析、模型和检索适配。Java SDK 与 Python SDK 使用同一套公共 API，企业可选择适合自身技术栈的集成方式。

### 5. 可扩展企业集成

当前提供带 HMAC 签名的 Webhook、事件筛选、投递重试、失败查询、资源删除级联和投递审计。后续可以在同一边界上扩展工单、CRM、IM、门户和数据平台连接器。

## 四、产品形态

```text
企业资料 / 图片 / 扫描件
            │
            ▼
知识库底座：解析 → 切片 → 审核 → 索引 → 发布
            │
            ├── 关键词 / 语义 / 混合检索
            ├── 有权限、有时效的引用问答
            ├── 反馈 → 改进任务 → 再发布
            └── API / Java SDK / Python SDK / Webhook
            │
            ▼
客服、售后、研发、培训、合规等业务应用
```

业务意图和 Agent 行为不放在底座中。未来的应用层可以根据企业业务配置“识别意图—调用知识—触发人工或业务系统”的流程，但模型输出不会自动获得权限，也不会直接执行敏感动作。

## 五、技术资产与壁垒

### 数据与版本资产

文档版本、切片修订、发布记录、引用证据、权限变更和反馈任务形成连续数据链。随着企业使用增加，系统可以积累真实的问题分布、资料缺口和改进历史，形成比单纯向量库更难迁移的知识治理资产。

### 安全与可追溯边界

授权在 Java 服务端逐项复核，客户端和模型都不能自称企业或用户身份。答案引用在交付前再次检查；删除、撤权、过期和归档会影响检索可见性。密钥不回显，敏感配置加密保存，备份和密钥轮换有明确运维流程。

### 可替换模型与存储

生成、Embedding、Rerank、对象存储、MySQL、RabbitMQ 和 Milvus 通过边界适配。企业可以接入 DeepSeek（当前生成配置示例为 `deepseek-v4-flash`）、自托管模型或其他批准的供应商，减少对单一模型厂商的锁定。

### 开源工程资产

项目采用 Apache-2.0，提供架构说明、ADR、API/OpenAPI、Java/Python SDK、迁移、恢复、贡献、安全和质量文档。CI 包含 Java、Python、Web、Milvus 集成、依赖审计和敏感信息扫描，便于客户自行审查和二次开发。

## 六、目标客户与使用场景

### 首要客户画像

- 有大量内部技术、产品或运营资料的中小企业；
- 需要私有化或内网部署的制造、软件、医疗服务、教育和专业服务组织；
- 已经尝试通用聊天机器人，但遇到权限、引用、版本和资料治理问题的团队；
- 希望把知识能力接入现有门户、客服系统或内部应用的技术团队。

### 首批场景

1. 售后人员查询产品型号、错误码和维修步骤；
2. 客服从经过审核的政策和 FAQ 中生成带引用的回复；
3. 研发人员查询接口规范、版本变更和故障处理记录；
4. 新员工培训和制度问答；
5. 合规或质量团队追踪资料版本、过期内容和回答反馈。

这些场景共同要求资料可靠、权限明确、答案可解释，适合先销售“知识底座”再扩展业务应用。

## 七、商业化假设

当前没有虚构收入、客户数或增长数据。可验证的商业化路径是：

1. **企业订阅或私有化授权**：按企业、知识库、成员规模或应用数量定价。
2. **实施与治理服务**：提供资料整理、权限设计、模型接入、迁移和质量运营服务。
3. **增值应用层**：在底座之上提供售后助手、客服助手、研发助手等行业应用。
4. **企业连接器与支持服务**：对接工单、CRM、IM、门户和审计系统，并提供版本支持与安全响应。

定价、毛利、销售周期和续费率需要通过试点客户验证，不在当前开发版本中预先承诺。

## 八、竞争定位

CareFlow 的差异化重点不是单次问答的演示效果，而是企业长期运行需要的控制面：

| 维度 | CareFlow 定位 |
| --- | --- |
| 知识生命周期 | 导入、解析、切片修订、版本发布、回滚和清理形成闭环 |
| 可信回答 | 证据引用、权限复核、有效期过滤、无证据拒答 |
| 企业治理 | 租户隔离、角色与应用授权、MFA、OIDC、审计和保留策略 |
| 技术选择 | 模型和存储可替换，支持云模型与自托管模型边界 |
| 集成方式 | 公共 REST API、Java/Python SDK、签名 Webhook |
| 开放性 | Apache-2.0，可审查、可扩展、可私有化部署 |

与只提供个人笔记或单一聊天入口的产品相比，CareFlow 更接近企业知识基础设施；与大型平台型产品相比，CareFlow 以可部署、可审查和较小的系统边界切入。具体竞品价格和市场份额需要在商业尽调阶段独立核实。

## 九、当前进展

- 已具备独立知识库底座、文档生命周期、解析/OCR、切片工作台、混合检索和引用问答。
- 已具备企业成员、角色、应用凭证、OIDC 外部身份绑定和 MFA。
- 已具备备份、恢复、备份密钥轮换、模型配置密钥轮换和数据保留/删除/脱敏/审计。
- 已具备答案反馈、改进任务、质量汇总和企业 Webhook 集成。
- Java、Python、Web 均有公共接口或 SDK；项目文档、许可证、贡献规则和安全渠道已建立。
- 本地验证覆盖 Java、Python、Web、敏感信息扫描和依赖漏洞扫描；GitHub 远端 Actions 及分支保护仍需仓库维护者凭据完成实际核验。

## 十、当前边界与主要风险

### 产品边界

当前版本面向单机、低并发运行，不承诺高并发容量、高可用 SLA、GPU 调度、视频转写、通用 Agent 执行平台或在线支付。业务意图识别和流程自动化属于上层应用方向。

### 技术风险

- 外部模型服务的价格、稳定性、数据处理政策和输出质量会影响客户体验；
- OCR 和复杂表格仍需要人工质量检查；
- 多租户规模扩大后，需要继续验证数据库、队列、向量库和对象存储的容量边界；
- 企业 SSO、密钥管理和备份恢复需要在客户环境中完成安全配置和演练；
- 人工评测集和真实客户质量基线仍需持续积累。

### 商业风险

- 企业知识治理通常需要较长的试点和采购周期；
- 开源版本需要建立贡献者、维护者和商业支持体系；
- 大型云平台可能把问答能力作为套件功能提供，项目需要持续证明私有化、可审查和跨应用底座的价值。

## 十一、建议的里程碑

1. **试点版**：选择一个资料边界明确的企业场景，完成从导入到发布、问答、反馈和改进的真实闭环。
2. **可交付版**：完成远端 CI/分支保护核验、清洁环境安装、备份恢复演练和客户安全评审材料。
3. **行业应用版**：在底座之上推出一个垂直应用，验证意图配置、业务路由和企业系统集成。
4. **规模化版**：根据真实客户数据决定是否投入高并发、托管服务、更多连接器和多区域高可用能力。

## 十二、资金使用方向

在获得试点和商业验证后，资金优先投入：

- 产品与开发者体验：安装、升级、管理界面和 SDK；
- 企业安全与合规：身份集成、密钥管理、审计和客户安全评审；
- 质量运营：行业测试集、人工评审和知识改进工具；
- 连接器与应用层：围绕首个垂直场景形成可复制方案；
- 客户成功与实施：资料迁移、知识治理和试点交付。

是否投入高性能基础设施，应以试点客户的真实需求和付费证据决定，而不是在单机开发阶段提前扩大系统复杂度。
