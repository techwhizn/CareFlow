# 运维与恢复运行手册

## 启动与健康状态

`docker compose ps` 检查基础设施；`docker compose logs --tail=100 backend worker-consumer worker-api` 检查无正文日志。上传后查看 `/api/v1/jobs/{id}`，不使用虚构进度百分比。索引和模型异常必须显式失败。端口绑定 loopback，Worker 端口不公开。

## 模型接入

`.env` 指定三个模型服务的地址、模型名称及密钥；Embedding 必须配置不可变 `EMBEDDING_REVISION` 与实际输出维度。真实模型接口需分别符合 embeddings、rerank、chat/completions SSE 契约。无配置时请求失败。供应商 API 未核验时禁止认定兼容；更换模型指纹必须重建并发布新的文档版本。

## 备份

1. 进入维护窗口，停用 API 写入入口，停止 consumer，等待 RUNNING 任务完成或租约失效。
2. `scripts/backup.sh <隔离备份目录>` 保存 MySQL 一致性逻辑快照。
3. 使用存储管理员工具为 S3 卷做快照，覆盖原文件；保存 `.env` 的加密副本到受控密钥存储，不能进入 Git。
4. 导出这次备份之后的删除、撤权、凭证撤销日志到独立于备份的持久记录。恢复时这些记录必须存在。
5. Milvus 可从切片重建；如需要保留旧模型 Collection，保留当时模型身份与服务的可访问版本。
6. 默认备份保留 30 天、审计元数据 180 天；当前版本未自动执行保留期限淘汰。

## 恢复验证（未执行，不是已验证恢复方案）

1. 建立隔离网络和空卷，禁止对业务开放入口。
2. 恢复 MySQL 与 S3。
3. 在任何索引重建与对外开放前重放最新删除、ACL 收窄、禁用成员和密钥撤销记录；无法得到最新日志就保持不可访问。
4. 所有 RUNNING 任务先失效旧租约，调度器重新投递。只重建未删除且被允许恢复的版本。
5. 验证对象摘要、租户隔离、历史答案隐藏、已删除对象不可见、模型身份一致，再执行真实 smoke。
6. 记录 RPO/RTO 和失败处置。本仓库尚无恢复演练数据，不能承诺 SLA。

## 已知运行限制

- 只配置了单机依赖；不提供高可用。
- 新上传采用暂存与补偿；旧版本遗留孤立对象仍需单独核对，不能盲目删除。
- 物理清理与备份撤权重放目前是运维契约，未自动实现。立即逻辑删除已实现。
- 查询次数与套餐资源限制已接入；企业公平调度见 [任务调度](task-scheduling.md)。处理资源细分计费、Redis 限流尚未闭环。
- 存量预占请求遭进程崩溃后需要人工核对释放，不能直接清零全部额度。

## 模型密钥存储与批准地址

`MODEL_CONFIG_ENCRYPTION_KEY`是标准Base64编码的32字节AES主密钥。新部署初始化脚本自动生成；已有部署需安全生成并配置，禁止写入Git、终端日志或普通数据库备份。丢失主密钥将无法恢复已存模型凭证，备份应保存受控加密副本。当前不支持直接更换主密钥后的自动重加密，不可盲目轮换。

`MODEL_EXTERNAL_BASES`默认仅批准`https://api.deepseek.com`；`MODEL_LOCAL_BASES`默认为空。两者是逗号分隔的精确base URL，仅根路径或/v1路径。部署管理员增加地址前检查所属方、TLS与数据外发策略；更改后重启后端。普通企业管理员只能在批准列表中选地址，不能任意探测内网。

模型注册页面保存企业级连接元数据和密钥，V1-02连接检测与V1-03知识库绑定尚未完成；当前Worker继续读取原有环境变量，不会因保存注册配置改变调用行为。

## 开通额外企业

登录页“初始化企业”模式中选择“开通另一企业”，由部署管理员提供开通密钥。使用新的独立租户ID和所有者凭证，不覆盖首次初始化企业。开通密钥仅用于部署运营，不发给普通企业成员。开通成功立即安全交付凭证；响应丢失时先核对开通请求记录，不能盲目换请求键再次开通。当前没有自动恢复丢失所有者凭证的公开接口。

成员状态变更后旧凭证失效；重新启用需显式签发新凭证。企业所有权转移尚未提供，系统禁止通过普通角色编辑破坏所有者约束。成员移除保留审计记录；知识库责任人需先移交，不能造成无人负责的资源。

## 应用密钥轮换

在应用中心按最小需要选择READ、SEARCH、ANSWER及期限签发新密钥。将新密钥安全交付对应调用方并验证后，在该应用的密钥列表撤销旧密钥。列表不显示密钥明文或摘要。服务端每次认证校验active、expires_at及应用发布状态，执行中的问答也重新认证。不要把原密钥写入日志或工单。

## 解析资源限制

部署可通过PARSE_MAX_PDF_PAGES（500）、PARSE_MAX_IMAGE_PIXELS（40000000）、PARSE_MAX_ARCHIVE_BYTES（209715200）、PARSE_MAX_ARCHIVE_ENTRIES（10000）、OCR_TIMEOUT_SECONDS（60）、PARSE_TIMEOUT_SECONDS（600）收紧限制，不能超过括号内默认硬上限。配置非法明确拒绝解析。

每份文档单独spawn进程，超时终止并回收；Linux子进程用PARSE_MEMORY_MIB（最大2048）限制地址空间及CPU秒数。Compose消费者限制2GiB内存、2核、128进程。macOS主机开发不执行Linux内存上限；不可把macOS测试当容器内存验收。PDF页像素在渲染前检查，Office先检查解压总量和条目数。OCR仍要求安装英文及简体中文Tesseract语言包。

Worker容器构建、真实中英文OCR及Linux资源限制已验证，见 [验收记录](reports/v1-13-ocr.md)。Docker Hub不可达时可使用 `docker compose build --build-arg PYTHON_IMAGE=public.ecr.aws/docker/library/python:3.12-slim worker-consumer`；随后仍需执行 [合成样例验证](../examples/ocr/README.md)。PARSE_TIMEOUT、PARSE_RESOURCE_LIMIT、INVALID_FILE、PARSING_FAILED是安全阶段错误码，不记录正文。解析失败不自动伪造结果。

## 上传暂存清理与任务恢复（V1-14）

对象存储调用已移出数据库事务。upload_staging记录唯一对象键和状态：PENDING（15分钟）、ATTACHED（已关联版本）、CLEANING（清理租约5分钟）、DELETED。每分钟扫描最多20个到期未挂接对象，事务内取得清理资格后在事务外删除对象；存储/进程失败可再次尝试。清理前再查版本引用，已挂接对象不删除；成功记录系统审计。不要手工复用暂存对象键。S3每个请求有120秒总超时，连接10秒、读写60秒。

若上传期间Java进程中断，PENDING到期后进入清理；如果数据库暂时不可用，保留原到期时间等待恢复。历史V10之前未记录的孤立对象不在本扫描范围，不能宣称已清理存量所有文件；V1-23负责整体物理清理与保留策略。

Worker检查点是阶段确认记录。解析重试从原文件开始，索引重试沿用不可变版本；数据回写由租约隔离及事务完成。每次领取重置检查点为STARTED，记录attempts；恢复始终先锁企业再锁任务，取消与完成采用相同锁顺序。

## 知识库归档、恢复与删除

先查看影响预览再操作；计数受当前身份授权限制。归档保留文件与发布版本，但查询和依赖历史立即隐藏，进行中的任务取消。恢复前确认责任人启用；恢复不重放旧权限或自动继续被取消任务。已过期文档与未就绪索引仍不参与检索。

删除写入持久化cleanup_requests（PENDING）并立即逻辑隔离。V1-23物理清理执行器与保留期尚未完成，不能宣称删除的正式知识数据已物理移除。upload_staging的补偿清理只处理未挂接上传，与正式资源删除不是同一流程。
