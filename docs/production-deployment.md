# 部署说明

CareFlow 当前公开验证范围是 Linux/amd64 单机、低并发部署。默认 Compose 适合开发和小规模内部使用；高并发、高可用、跨区域和 GPU 容量不属于当前版本承诺。

## 服务边界

- Java Backend：身份、授权、租户、元数据、任务、发布、计量和公共 API。
- Python Worker：解析、OCR、切片、模型适配、Milvus 检索和生成适配。
- Web：只调用公共 Java API，不直接访问数据库、对象存储或内部 Worker API。
- MySQL：业务状态和审计；RabbitMQ：任务消息；对象存储：原始文件；Milvus：向量和关键词索引。

## 部署前检查

1. 使用受支持的 Java、Python、Node 和 Docker 版本；兼容范围见 [本地制品说明](local-artifacts.md)。
2. 为数据库、队列、对象存储、Milvus 和模型服务准备持久卷与网络策略。
3. 用随机值替换所有引导、内部服务、对象存储和模型凭证；凭证不写入 Compose 文件或仓库。
4. 配置 `MODEL_CONFIG_ENCRYPTION_KEY` 并安全保存备份；丢失主密钥无法恢复已加密的模型凭证。
5. 先在隔离环境执行迁移、导入、索引、发布、撤权和恢复演练，再开放业务入口。

## 网络与权限

公共入口只暴露 Web 和 Java API。Worker、数据库、队列、Milvus 和对象存储使用内部网络；管理端口限制到运维网段。生产反向代理应启用 TLS、请求体限制、超时和访问日志脱敏。客户端传入的 tenant/user 字段不参与可信认证，授权由服务端凭证和数据库关系决定。

## 升级与回滚

数据库只按 Flyway 顺序前进，禁止修改已应用迁移。升级前执行停写备份并记录版本、镜像摘要和配置快照。回滚必须恢复匹配的应用、数据、索引和模型身份，不能只降低 Java JAR 版本。详细步骤见 [恢复手册](recovery.md) 和 [运维手册](operations.md)。

## 容量边界

本地 BGE Rerank 在有限 CPU 上适合低并发功能验证；并发请求可能显式返回模型不可用或忙碌错误。不要用关键词单路、隐藏 503 或伪造结果绕过这一边界。需要更高负载时，由部署者提供有足够容量的外部 Rerank/GPU 服务，并按自己的数据和错误预算重新验证。
