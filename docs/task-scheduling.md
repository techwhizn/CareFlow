# 租户公平任务调度

Java 的 FairTaskDispatcher 持有持久化轮转游标：按企业 ID 依次检查任务，走到末尾后回到开头。一个企业批量上传不会把其全部通知先塞进共享队列。每轮最多检查 100 次、发布 20 条，重复遇到已等待企业时结束本轮；轮次之间游标保留，调度器重启不重新偏向队首企业。

## 资源与等待

- 每家企业最多一个尚未被 Worker 领取的通知预留；RUNNING 任务另受套餐处理并发限制。
- 全局最多 32 个有效的 QUEUED 通知预留，防止主动无限灌入消息队列。该上限不是 RabbitMQ 历史重复消息总数限制，也不是全局运行并发承诺。
- 调度检查套餐状态、处理额度和运行并发，领取时在租户锁内再次检查并扣一次处理任务额度。
- 已扣额的内部重试优先于新任务，避免额度耗尽后被未扣额任务挡住；最多三次尝试仍由 Tasks 控制。
- 无额度或暂停企业保持 QUEUED，不增加 attempts、不再次扣费。等待原因由公共任务查询返回，任务中心显示。
- Worker 对明确的 ENTITLEMENT_INACTIVE / QUOTA_EXCEEDED 领取响应确认当前通知，释放共享队列；未知认证或网络错误不会静默确认。

后台等待原因：TENANT_NOTIFICATION_PENDING、ENTITLEMENT_INACTIVE、TASK_QUOTA_OR_CONCURRENCY、WAITING_FOR_WORKER。等待原因是最近调度观察值，恢复套餐后会在后续调度更新，不是实时指标。

## 故障恢复与锁顺序

通知预留有效 120 秒，与执行任务的 90 秒租约不同。预留提交后才进行 RabbitMQ 网络调用。消息确认、Java 崩溃、通知丢失、队列消费失败均不会丢掉数据库中的 QUEUED 任务；预留过期即可重新通知，包括已经标记 sent 的 outbox。outbox 保留原始持久事件，sent 表示曾确认，不代表任务完成。

通知 token 防止旧发布确认覆盖新一轮投递。Worker 仍以任务 ID 领取，租约防止重复执行、迟到回写；通知可能至少一次投递，不声称恰好一次消息传输。

调度选择依次锁全局游标、企业、任务；消息确认仅锁企业、任务。网络调用不持锁。多个 Java 实例共享游标与预留，因此不能同时给同一企业积累通知。

默认每 5 秒调度一次。公平性指有限任务执行后其他可运行企业可获得机会，不保证长任务中途抢占；单个消费者只能顺序处理，吞吐和时延还取决于消费者数与任务执行时间。已有解析超时、页面、像素、展开大小和 Linux/容器资源限制继续适用；真实 Linux/OCR 验收仍见 V1-13。

## 升级

V13 新增游标表、任务通知预留/等待字段和索引，不删除历史消息或任务。升级应在维护窗口停止旧调度器与消费者，完成 Java、Python 升级再启动；不要同时运行旧 FIFO 调度器与新轮转调度器。旧队列消息可被新消费者安全重复领取或忽略，不清空业务队列。回退应用保留迁移字段，但公平性与等待确认行为不再适用。
